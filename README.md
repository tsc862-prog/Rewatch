# MMA Rewatch

Static MMA rewatch tracker connected to Supabase. Serve this directory with a local HTTP server to preview it.

## Ratings

Ratings are unique per `(user_id, fight_id)`; ownership is required. Existing ownership RLS policies protect reads and writes. The Supabase migration `ratings_unique_per_user_and_fight` was applied on September 7, 2026, preserving all 1,235 existing ratings.

Rating and note edits share a serialized queue per user/fight. Edits during a request merge into the next write. Failed edits remain pending and the next rating/note edit retries them; an error toast explains this. Navigation or page closure is not an offline persistence mechanism. Writes use the composite conflict target and return the saved row. Note-only edits omit the rating so they preserve its stored value. Account changes prevent stale responses from updating another user's cache.

## Responsive layout

At widths up to 1,000px, navigation wraps below the header and matchups occupy their own row. Narrow cards wrap names and results. Header margins stay inside the document width.

## Checks

Run `node tests/rating-saves.cjs` for delayed-save, overlapping-note, retry, and account-switch regression checks, `node tests/crowd-blend.cjs` for the crowd score and bonus tags, `node tests/odds.cjs` for the betting lines and the UPSET tag, `node tests/summary.cjs` for the row's summary-and-notes panel and its rating gate, and `node tests/weight.cjs` for weight-class labels and grouping across eras.

## Fight table

The event card and the fighter card list fights as one flat table, and every bout gets the same row whatever its billing. Columns: the bout number (the date on the fighter card), the fighters stacked with their betting line, the weight class with the billing underneath (the event name on the fighter card), your star rating, the other users' average, the result, the watch icons, and an arrow that opens the fight's summary and your notes. On the event card a rated row is tinted green and the winner is bold with a tick. On the fighter card green would read as a win, so the tint follows that fighter's outcome once the result is showing (green win, red loss, amber draw) and the result column leads with a Win / Loss chip. The column template is one CSS variable on `.fight-table` (`.by-fighter` for the fighter card) shared by the header and every row; below 900px the header goes and each row stacks into a small card. The fighter card's profile is a band across the top with the table full width below it: the photo, name and bio pills, a row of spoiler-free career facts from `fighterCareerFacts()` in `js/fighter.js` (fights listed, years active, main division, title fights, last and next fight, how many are left to watch), the organisations fought for, and the viewer's own stats. `renderFightRow()` and `fightTableHeadHtml()` in `js/events.js` hold the row.

## Weight classes across eras

A class name has not always meant the same weight: a UFC "Middleweight" bout in 1999 was under 200 lb. A `fight_search` row therefore carries the name the bout was billed under (`weight_class`) and, where the scraper knows it, the upper limit it was fought at (`weight_limit_lb`). `weightLabel()` in `js/app.js` shows the limit beside the name only when it differs from today's limit for that name ("Middleweight · 200 lb"), and `weightGroup()` maps the row to today's nearest class for anything that counts or groups by division (the fighter card's main division, the dashboard's weight-class bars), so that 1999 bout counts with Light Heavyweight. Rows with no limit are today's classes and read as before.

## Crowd score

Every past fight row can carry a number in the Others column: the **other users' average rating** for that bout on the 0–5 star scale. The app has no real user base yet, so that average is currently sourced from Verdict MMA's fans (`crowd_rating` 0–10 and `crowd_rating_count` on `fight_search`, scraped nightly by the scraper repo's `verdict_scraper.py`), halved to stars. It is shown as-is and is never blended with the viewer's own rating; the tooltip says where it comes from, with the raw score and the number of fans. When real users arrive, `crowdScore()` should read an RPC that averages other users' ratings (excluding the viewer) with the crowd; nothing else in the row changes. UFC bonus awards (`bonus_awards`: `FOTN`, `POTN`, `KOTN`, `SOTN`) are each a tag on the second line of the Result column, with the full name in the tooltip. Both the number and the tags sit behind the row's spoiler gate: while the result is hidden ("Rate to reveal") nothing is shown at all, since a crowd score reveals whether the fight was any good and a bonus name reveals a finish; they appear with the result once the fight is rated. `crowdScore()`, `crowdScoreHtml()` and `bonusTagsHtml()` in `js/events.js` hold this. Tables and view columns were added on September 16, 2026 (scraper repo `migrate/add_crowd_ratings.sql`).

Every fight row also carries each fighter's **closing betting line** at the right end of the fighter's line: `−209` for the favourite, `+169` for the underdog, American odds. It comes from BestFightOdds via `fighter1_odds_close` / `fighter2_odds_close` on `fight_search` (the midpoint of BFO's closing range; `fighter1_odds_open` / `fighter2_odds_open` are the openers, shown in the tooltip when they differ), scraped nightly by the scraper repo's `bfo_scraper.py`. The line is deliberately **not** behind the spoiler gate: odds are public before the bell and reveal nothing about the result, so hidden-result rows show them too, and an upcoming fight shows its current line (the tooltip says "Current line"). An **UPSET** tag, in the bonus-tag family beside them, marks a winner who closed as the underdog while the loser closed as the favourite; that does give the result away, so it sits behind the spoiler gate with the bonus tags. `fmtOdds()`, `oddsHtml()`, `upsetPrice()` and `upsetTagHtml()` in `js/events.js` hold this. Table and view columns were added on October 6, 2026 (scraper repo `migrate/add_fight_odds.sql`).

The Community tab uses the same crowd ratings as its "other users": while the app has no real user base, `community_dashboard()` reads each fight's average and count from `fight_crowd_ratings` (halved to stars) instead of the `ratings` table, so the community average, the highest-rated fights (20+ ratings), cards (5+ rated fights) and fighter averages all reflect Verdict MMA fans, 2025 onward. The tab's header says so. Swap the RPC's source subquery back to `ratings` when real users arrive (scraper repo `migrate/community_crowd_ratings.sql`). Tables and view columns were added on September 16, 2026 (scraper repo `migrate/add_crowd_ratings.sql`). Preview event/fighter pages at phone and desktop widths when changing layouts.

## Fight summaries

A fight row can carry a short written **summary** of how the bout played out (2–4 sentences), read from a `summary` text column on `fight_search`. It lives in the row's detail panel, which the arrow at the end of the row opens, alongside the viewer's own notes box; the panel is collapsed by default. The gate is stricter than the result gate: the summary needs the viewer's own star rating, even on rows whose result is already shown because the fight has no watch link. Until then the panel says "Summary appears here once you rate the fight." and the text is not rendered into the page. A fight with no summary opens to the notes alone, and an upcoming fight has no arrow. A red dot on the arrow marks a fight the viewer has a note on. Open panels are remembered per fight for the session, so the re-render that follows each rating or notes save does not collapse them. `detailToggleHtml()`, `detailBodyHtml()` and `toggleFightDetail()` in `js/events.js` hold this. The text lives in the `fight_summaries` table and is written by the scraper repo's `summary_scraper.py`: a Claude model summarises Sherdog's round-by-round play-by-play for the card. The table and the view column were added on November 21, 2026 (scraper repo `migrate/add_fight_summaries.sql`). A fight the job has not covered yet has no summary.

The same row can also carry **pre-fight context**: `fighter1_missed_weight` / `fighter2_missed_weight` and `fighter1_short_notice` / `fighter2_short_notice` on `fight_search`, plus a one-sentence `context`. A fighter who missed weight gets a red MISSED WEIGHT tag on their line and a late replacement a blue SHORT NOTICE tag, with the sentence as the tooltip and as a grey line at the top of the detail panel. These were known before the bell, so unlike the summary they are not gated. On the fighter card the profile fighter has no line of their own, so their tags sit under the opponent's line with the surname in front. The flags come from the same scraper run as the summary and are false when the source did not say, so a missing tag is not proof a fighter made weight.

## Database deployment order

Apply the unique-per-user migration before deploying this frontend. The old single-fight constraint must be removed, and `(user_id, fight_id)` must be unique for the upsert conflict target. The live migration added `ratings_user_id_fight_id_key`, set `user_id NOT NULL`, and dropped `ratings_fight_id_key`. Database verification used temporary ratings in a rolled-back transaction to verify two users rating one fight and RLS read/update isolation.

Header padding is container-relative (24px on desktop), so ultrawide viewports do not squeeze the logo, navigation, or account controls.

The MMA Rewatch identity uses `img/brand-mark.svg`: a closed coral octagon with twin rewind chevrons. The header, login screen, page title, and favicon share this identity.

## Watch links and spoilers

Every fight row shows compact per-platform watch icons. A fight's own video (`paramount_url`, `fightpass_url`, `youtube_url`, `pluto_url` on `fight_search`) is used when present. When a fight has no dedicated video on any platform but its event has a replay (`event_<platform>_url` on the same row), the event links take the icons' place, outlined in the platform colour with a "Full event on …" tooltip. A fight with its own video shows only its own links; the event replay is a stand-in, never an extra. A full-card replay wins over a prelims replay; a prelims-only link is still shown, labelled "Prelims on …", because the database cannot tell which card segment a fight sat on. The main event row (`is_main`, `fight_position_type` "Main Event", or `fight_position` 1) is the exception: it never sat on the prelims, so it skips prelims links.

A row with any watch link, fight-level or event-level, hides its result behind "Rate to reveal result" until the fight is rated. A row whose event is dated today (local time) is hidden the same way whether or not it has any watch link yet, since the card is airing and the scraper may already have posted results; rating the fight still reveals it. This applies on the fighter card as well as the event card, since the row reads the event links from its own `fight_search` record rather than from the currently open event. `fightWatchLinks()` and `watchIconHtml()` in `js/app.js` hold this logic. The view columns `event_espn_url`, `event_espn_prelims_url`, and `event_netflix_url` were added on September 7, 2026 (scraper repo `migrate/add_event_vod_columns.sql`).

## Loading states

Every screen that waits on the database shows the shared spinner (`loadingHtml()` in `js/app.js`, the `.dash-loading` block) instead of sitting still or showing an empty state early: the events list on first load (one `events_index()` call), event search, the event card and fighter card (via `showCardLoading()`, which swaps the search card out the moment a row is clicked), the My Ratings table before ratings arrive, the rankings tab while its snapshot index loads, and the dashboard activity feed. The dashboard and community tabs already had inline spinners. Card loads check that the user has not opened something else before painting, and restore the search card on error.

## Load performance

Each screen makes one request against precomputed data instead of assembling it client-side. `events_index()` returns every event with `has_results` / `has_fight_video` flags as a single JSON array (it replaced a fights count, an `event_result_flags` aggregate, and paging the events table down 1000 rows at a time, which together took 3 to 4 seconds). `my_ratings()` returns the signed-in user's ratings already joined to `fight_search`, newest first, in the same `{ ...fight, ...rating }` shape the app caches (it replaced a ratings query followed by chunked `fight_search` lookups). `community_dashboard()` keeps its signature but reads the `community_fight_base` materialized view.

The flags and the community base are materialized views in Supabase, refreshed by `refresh_app_caches.py` in the scraper repo at the end of every scraper pass (nightly workflow and the live-event loop). Between passes the Past list and Community stats reflect the last refresh; an open event card always reads live rows. The migration is `migrate/app_perf_precompute.sql` in the scraper repo and must be applied before deploying this frontend (added September 16, 2026).

`init()` in `js/app.js` fires every initial request at once and does not wait for the events list before marking ratings-dependent screens ready. supabase-js is pinned to an exact version, all scripts are `defer`red, and Chart.js is loaded on first use by `ensureChartJs()` rather than on every page view.
